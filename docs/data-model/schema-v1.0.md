# Relational Data Model v1.0

**Status:** Accepted v1.0  
**Date:** 2026-10-04  
**Database:** PostgreSQL 18  
**Related ADRs:** ADR-003, ADR-006, ADR-011  
**Supersedes:** schema-v0.1.md once accepted

This document converts the accepted domain model, state machines and UX flows into a migration-ready relational design.

The goal is not to predict every future feature. The goal is to freeze the MVP schema boundaries strongly enough that Flyway migrations and API contracts can be generated without re-litigating the domain model.

# 1. Global conventions

## 1.1 IDs

Use `uuid` primary keys for business entities.

Human-readable values such as Trailer number, Tractor number and Order number are never primary keys.

UUIDs may be generated by the application or PostgreSQL, but the choice must be consistent in implementation.

## 1.2 Timestamps

Use `timestamptz` for persisted event/transaction timestamps.

Persist timestamps in UTC.

Store an IANA timezone on Physical Sites because appointments and operational display are location-sensitive.

## 1.3 Mutable aggregates and optimistic locking

Mutable aggregate-root/current-state tables include:

```text
version bigint NOT NULL DEFAULT 0
```

JPA optimistic locking should use this value to prevent silent overwrite when two users change the same resource.

Primary candidates:

- tenant_settings;
- customers;
- physical_sites;
- operational_locations;
- drivers;
- tractors;
- trailers;
- orders;
- trips;
- trip_stops;
- yard_checks;
- alerts.

## 1.4 State/value representation

Application lifecycle states are stored as `varchar` values mapped to Java enums using string representation.

Do not use ordinal enum persistence.

For stable closed state sets, add PostgreSQL `CHECK` constraints in Flyway migrations.

Do not use PostgreSQL native enum types for MVP because schema evolution is easier with varchar + checks.

## 1.5 Tenant consistency

Every tenant-owned table contains:

```text
tenant_id uuid NOT NULL
```

For high-value parent/child relationships, use composite tenant-safe foreign keys where practical.

Pattern:

```text
parent:
  UNIQUE (tenant_id, id)

child:
  FOREIGN KEY (tenant_id, parent_id)
    REFERENCES parent (tenant_id, id)
```

This prevents a Tenant A child row from referencing a Tenant B parent even if application authorization fails.

## 1.6 Delete policy

Operational records are not physically deleted during normal use.

Prefer:

- status;
- active flag;
- disabled timestamp;
- explicit retention jobs.

Foreign keys for operational/history records should generally use `RESTRICT` / no destructive cascade.

## 1.7 Audit/source metadata

Operational/event records should distinguish:

- HUMAN_USER;
- SYSTEM;
- INTEGRATION.

Historical actor references must survive user disablement.

# 2. Identity and tenancy

Global authenticated identity.

A User has no Tenant access by itself.

## tenants

```text

updated_at          timestamptz NOT NULL
```

Candidate status:

- ACTIVE
- SUSPENDED
- DISABLED

Other settings should be added only when approved instead of storing an unconstrained configuration blob.

## role_assignments

A membership may hold multiple roles.


- TENANT_ADMIN
- TRANSPORT_OPERATIONS

- TENANT
- CUSTOMER

Constraint:

- CUSTOMER scope requires `customer_id IS NOT NULL`;
- TENANT scope requires `customer_id IS NULL`.

# 16. Referential integrity rules worth enforcing in SQL

The migration set should enforce at least:

1. all core child rows reference parents in the same Tenant;
2. only one open Shift per Driver;
3. only one active coupling per Trailer;
4. only one active Trailer coupling per Tractor;
5. Yard Check has at most one item per Trailer;
6. Trip has unique Stop sequence numbers;
7. Trailer operational number is tenant-unique for MVP;
8. LOCATION_UNKNOWN has no current_location_id;
9. AT_LOCATION requires current_location_id;
10. role scope/customer nullability is consistent;
11. no duplicate client operation ID per Tenant;
12. one delivery_evidence row per delivery Stop.

Some state-machine invariants require application transaction logic rather than CHECK constraints and must be covered by integration tests.

# 17. Concurrency strategy

Use optimistic locking for user-edited aggregates.

Examples:

- Dispatcher A and Dispatcher B edit same Trip;
- Admin changes Trailer while Yard Spotter is offline;
- Customer changes Order while Transport Operations is planning it.

If `version` changed:

- reject stale command;
- return a conflict response;
- client refreshes and reconciles.

Physical movement commands also validate current state transactionally before writing state + event.

# 18. Transaction boundaries

Examples that must be atomic:

## Hook Trailer

One transaction:

1. validate authorization/state;
2. validate no conflicting active coupling;
3. create coupling;
4. append HOOKED event;
5. update Trailer current projection;
6. record processed client operation when mobile-originated.

## Drop Trailer

One transaction:

1. close coupling;
2. append DROPPED event;
3. set current location/state;
4. update last-seen/current projection;
5. record idempotency result.

## Mark Location Unknown

One transaction:

1. preserve last-known values;
2. clear current location;
3. set LOCATION_UNKNOWN;
4. append movement event;
5. create Admin alert;
6. write audit/reconciliation context.

## Complete Delivery

One transaction after required uploads are finalized:

1. validate required evidence;
2. create delivery_evidence;
3. transition Stop to COMPLETED;
4. append Stop event;
5. update Order fulfillment projection/status;
6. possibly complete Trip if no work remains.

# 19. RLS boundary

PostgreSQL Row Level Security is not activated by this schema document.

Primary tenant enforcement is:

- application authorization;
- tenant-safe SQL filters;
- composite tenant-safe foreign keys.

RLS remains an approved defense-in-depth candidate and requires a separate ADR because connection-pool/session-context handling must be proven safe.

# 23. Schema freeze acceptance criteria

Schema v1.0 can be marked Accepted when:

1. every Accepted MVP UX flow can persist the data it needs;
2. every Accepted state machine has explicit persisted state/current projection;
3. tenant/customer scope is enforceable;
4. offline idempotency is representable;
5. operational history is preserved without full event sourcing;
6. no MVP workflow requires an undocumented polymorphic core relationship;
7. foreign-key/uniqueness strategy prevents obvious cross-tenant corruption;
8. concurrency strategy is defined;
9. Flyway migrations can be derived directly from this document;
10. remaining open questions are policy-level and do not require a domain redesign.

# Tenant Admin Web — UX Flow v0.1

**Status:** Accepted v0.1  
**Primary actor:** TENANT_ADMIN  
**Related requirements:** FR-001–021, FR-090–103, FR-160–174, FR-180–186  
**Related security docs:** ADR-011, tenancy-and-authorization, permission-capabilities

## Goal

Give the subscribing transportation/logistics company a secure administrative workspace to manage:

- users and memberships;
- roles and permissions;
- Customers;
- Drivers;
- Tractors;
- Trailers;
- Sites / Yards / Docks;
- tenant settings;
- operational alerts;
- audit/history.

This workspace is administrative. It should not replace the day-to-day Transport Operations dispatch workflow.

# 2. Admin dashboard

## Purpose

Give a high-level operational/administrative health view.

## Required cards/sections

- Active users;
- Active Drivers;
- Tractors;
- Trailers;
- Customers;
- Open Alerts;
- Missing / Location Unknown Trailers;
- Out-of-Service Trailers;
- recent administrative changes.

Do not turn this into a large BI/reporting product in MVP.

---

# 3. Users & Access

## Users list

Show:

- name;
- email;
- membership status;
- role assignments;
- customer scope where applicable;
- last updated;
- enabled/disabled status.

Filters:

- role;
- status;
- customer scope.

Primary actions:

- Invite User;
- Edit role assignment;
- Suspend/Disable membership;
- View access details.

## Invite User

Fields:

- email;
- display name;
- Tenant;
- role assignment(s);
- Customer scope if role requires it.

Examples:

```text
Role: CUSTOMER_DISPATCHER
Customer: Hood Container
```

or:

```text
Roles:
- TRANSPORT_OPERATIONS
- YARD_SPOTTER
```

The UI should permit multiple role assignments.

## Membership states

Display clearly:

- INVITED
- ACTIVE
- SUSPENDED
- DISABLED

Disabling a user must not erase historical actor references.

## Role assignment UX

Do not expose raw capability codes to ordinary Admin users in MVP.

Admin selects system roles; UI can show a readable summary of what that role permits.

Future custom roles are out of scope for MVP.

# 4. Customers

## Customers list

Show:

- Customer name;
- active/inactive;
- designated Trailer count;
- Site count;
- user/contact count.

Primary actions:

- Add Customer;
- Edit Customer;
- View Customer.

## Customer detail

Sections:

### Overview

- name;
- status;
- operational summary.

### Customer users

- Customer Dispatchers;
- invitation/status;
- scoped access.

### Sites

- associated Physical Sites;
- Customer Operational Areas;
- Yard/Dock relationships.

### Designated Trailers

- Trailer number;
- current location;
- load state;
- serviceability.

### Recent Orders

Read-only operational summary with link to Operations.

# 5. Drivers

## Driver list

Show:

- name;
- active status;
- license number;
- medical certificate expiration;
- linked app User/account status;
- default/current Tractor association if known.

Filters:

- active/inactive;
- certificate expiry attention;
- account linked/unlinked.

## Driver detail

Sections:

- profile;
- license;
- medical certificate expiration;
- linked User;
- current/on-duty state;
- recent Trips;
- recent Pre/Post-Trip records.

Admin actions:

- create/edit Driver;
- activate/deactivate;
- link/invite Driver User.

Do not expose payroll calculations.

---

# 6. Tractors

## Tractor list

Show:

- operational number;
- active status;
- associated/default Driver when applicable;
- current assigned Trip if active;
- latest odometer observation.

Admin actions:

- create/edit Tractor;
- activate/deactivate.

No maintenance work-order system in MVP.

---

# 7. Trailers

## Trailer list

Columns/fields:

- operational number;
- designated Customer;
- current location;
- load state;
- coupling state;
- serviceability;
- last seen;
- current/last Driver.

Filters:

- Customer;
- location;
- load state;
- OOS;
- Location Unknown;
- coupled/uncoupled.

Primary actions:

- Add Trailer;
- Edit Trailer metadata;
- Change designated Customer;
- Mark OOS;
- Return to Service where policy permits;
- View history.

## Add/Edit Trailer

Fields:

- operational number;
- designated Customer;
- type/size;
- special capability notes;
- active status.

QR identity:

- generated by system;
- view/print/reissue/revoke flow can be exposed separately.

Do not use operational number as technical identity.

## Change designated Customer

This is an explicit administrative action.

Show:

- current Customer;
- new Customer;
- reason.

Require confirmation.

Result:

- designation changes;
- audit event written;
- current Order/load/location remains unchanged unless a separate operational action changes it.

---

# 8. Locations

## Physical Sites

List:

- name;
- address;
- timezone;
- geofence configured yes/no;
- active.

Admin actions:

- create/edit Site;
- configure geofence center/radius.

## Operational Locations

Within a Site, manage:

- Yards;
- Docks;
- Customer Areas;
- Base;
- Shop/Other.

Each location can optionally be associated to a Customer.

Example:

```text
710 Kimberly Dr
├── Stanfast Yard
├── Stanfast Dock 14
├── Stanfast Dock 15
├── Black Hawk Yard
├── Black Hawk Dock 1
└── Black Hawk Dock 2
```

Do not duplicate the physical Site just because customer operational areas differ.

---

# 9. Alerts

Admin has tenant-wide alert access.

Show:

- alert type;
- related Trailer/Trip/etc.;
- severity;
- OPEN / ACKNOWLEDGED / RESOLVED;
- created time.

Primary actions:

- Acknowledge;
- Open related resource;
- Resolve when manual resolution is permitted.

Important examples:

- TRAILER_MISSING;
- STALE_TRAILER;
- OPERATIONAL_EXCEPTION.

---

# 10. Audit

## Audit list

Show:

- timestamp;
- actor;
- action;
- entity;
- summary.

Filters:

- date/time;
- actor;
- entity type;
- action type.

## Audit detail

Show:

- previous data where applicable;
- resulting data;
- actor;
- timestamp;
- reason;
- source type.

Audit UI is read-only.

Do not provide a generic "undo" unless a specific business correction command exists.

---

# 11. Settings

MVP settings should expose only approved tenant-level configuration.

Candidate settings:

- stale Trailer threshold;
- alert recipients;
- Site/geofence defaults;
- inspection checklist content once finalized;
- retention values only if legally/product approved;
- account/company profile.

Do not expose unsupported configuration merely because the data model could store it.

---

# 12. Validation and error UX

## Cross-scope protection

Admin is tenant-wide but never cross-tenant.

If a resource is not part of the active Tenant, do not expose its metadata.

## Conflict

If another user changed the same master record:

```text
This record changed while you were editing it.
Review the latest version before saving again.
```

## Destructive actions

Prefer deactivate/disable over delete for records referenced by operational history.

Examples:

- Driver;
- Tractor;
- Trailer;
- Customer;
- User membership.

---

# 13. MVP exclusions

Not included in Admin UX v0.1:

- custom-role builder;
- billing/subscription management;
- accounting;
- payroll;
- maintenance work orders;
- complex analytics;
- Samsara/Amtech integrations.

---

# 14. Acceptance criteria for wireframing

Ready for wireframes when:

1. Admin can invite/disable users and assign system roles.
2. Customer-scoped users can be assigned to a specific Customer.
3. Admin can manage Customers, Drivers, Tractors, Trailers and Locations.
4. Trailer designation changes are explicit and audited.
5. Physical Site and Operational Location remain separate concepts.
6. Alerts and Audit are visible tenant-wide.
7. Historical entities are deactivated rather than destructively deleted by default.
8. No screen exposes raw tenant IDs as an authorization mechanism.
